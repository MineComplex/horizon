# Porting Leaf to Rust: the rules

`horizon-server` is Leaf 26.3 (its applied sources: the patched NMS, Leaf's own code, Paper's server code
and paper-api) ported line for line to Rust in one crate. The Java in `~/Desktop/new/Leaf` is the
specification. Leaf's **finished** code is ported: no patch system, and no vanilla sources or other
Horizon crates as reference (this crate depends on none of them).

The Bukkit/Paper API keeps its exact shape (`crate::org::bukkit`, `crate::io::papermc::paper`...), but there
is no CraftBukkit wrapper layer: the NMS types implement the API traits themselves
(`impl org::bukkit::entity::Player for ServerPlayer`). CraftBukkit's code is the reference for those impls
and for event firing (`crate::api_impl`, which keeps CraftBukkit's non-wrapper classes: `CraftEventFactory`,
`CraftMagicNumbers`, `Main`...).

## Layout

- One Java file = one Rust module at the same package path. `net/minecraft/world/entity/Entity.java` ->
  `src/net/minecraft/world/entity/entity.rs` (`crate::net::minecraft::world::entity::entity`). Each package's
  `mod.rs` re-exports its types, so `crate::net::minecraft::world::entity::Entity` works too.
- CraftBukkit (`org.bukkit.craftbukkit.X`) -> `crate::api_impl::X` (wrapper classes are not ported as types).
- Nested types live in the outer file's module, named Outer+Inner: `BlockPos.MutableBlockPos` ->
  `BlockPosMutableBlockPos`, `Entity.RemovalReason` -> `EntityRemovalReason`.
- Names: methods and fields `snake_case` (`getXRot` -> `get_x_rot`), Rust keywords get a `_` suffix (`type_`),
  types keep their Java name (a few that clash with Rust's prelude get `J`: `OptionJ`).
- **Look names up, never guess:** `python3 tools/leaf_port/q.py <Type>` / `<Type>.<method>` prints the Rust
  path, trait, fields and every method's Rust name (overloads are `name`, `name_3`... by arity, fixed per
  hierarchy). The skeleton every file starts from was generated by `tools/leaf_port/gen.py`.
- External libraries keep their Java package paths too: `crate::com::mojang::serialization::Codec`,
  `crate::com::mojang::brigadier`, `crate::io::netty::buffer::ByteBuf`, `crate::net::kyori::adventure`,
  `crate::org::joml`, `crate::com::google::gson`, `crate::java::util::concurrent::CompletableFuture`. Where a
  package only has `ext_stubs.rs`, the library port replaces those stand-ins.

## Types

| Java | Rust |
|---|---|
| `int long short byte char boolean float double` | `i32 i64 i16 i8 char bool f32 f64` (boxed ones too) |
| `String`, `CharSequence`, `StringBuilder` | `String` (fields, returns); `&str` parameters |
| class (non-polymorphic) | `JRef<C>` (`Arc<C>`) |
| polymorphic class (abstract or subclassed) | `JRef<dyn CTrait>` |
| interface | `JRef<dyn I>` |
| record, enum, value class (all-final fields of values: `Identifier`, `Vec3`, `BlockPos`, `AABB`...) | by value `C` (Clone; Copy when all fields are) |
| `@Nullable T` | `Option<T>` |
| `T[]`, `List`, `Collection`, `Iterable`, `ImmutableList`, fastutil lists | `Vec<T>` |
| `Set`/`HashSet` / `LinkedHashSet`, `ImmutableSet` / `TreeSet` | `HashSet` / `IndexSet` / `BTreeSet` |
| `Map`/`HashMap` / `LinkedHashMap`, `ImmutableMap` / `TreeMap` | `HashMap` / `IndexMap` / `BTreeMap` |
| fastutil `Int2ObjectMap<V>`, `Long2LongMap`... | `HashMap<i32, V>`, `HashMap<i64, i64>` (Linked -> `IndexMap`) |
| `Multimap<K,V>` | `IndexMap<K, Vec<V>>` |
| `Deque`, `Queue`, `ArrayDeque` | `VecDeque<T>` |
| `Optional<T>`, `OptionalInt` | `Option<T>`, `Option<i32>` |
| `Map.Entry<K,V>` | `(K, V)` |
| `UUID` | `Uuid` |
| `Object` | `JObjectRef` (`Arc<dyn JObject>`) |
| `Runnable`, `Supplier<T>`, `Function<A,B>`, `Predicate<T>`... | `JRef<dyn Runnable>`... traits with closure impls: pass `Arc::new(\|x\| ...)` |
| `AtomicInteger/Long/Boolean`, `ConcurrentHashMap` | `AtomicI32/I64/Bool`, `dashmap::DashMap` |
| `File`, `Path` | `PathBuf` |
| `Throwable` and exceptions | `crate::java::lang::Throwable` |
| Java type parameter `T` | Rust `T: JGeneric`, instantiated with the full Rust type (`EntityType<JRef<Zombie>>`) |
| `?`, `? extends X` | `X`'s Rust type, or `JObjectRef` |

## Objects

- Every method takes `&self` (value types: `&self`, or `&mut self` when they assign their own fields; enums:
  `self`). A field Java assigns after construction, and any collection field, is `Mut<T>`:
  `this.x` -> `self.x.get()`, `this.x = v` -> `self.x.set(v)`, `this.list.add(v)` -> `self.list.borrow_mut().push(v)`.
  Keep `borrow_mut()` borrows to one statement; never hold one across a call that can reach this object again.
- `this` as a value: `self.this()` (the object's own `JRef`, from the `this: Weak<..>` field every reference
  type has).
- `synchronized` -> a `Monitor` field (`let _g = self.monitor.lock();`); `volatile` -> `Mut` or an atomic.

## Inheritance

`class Zombie extends Monster`:

```rust
pub struct Zombie { pub base: Monster, pub this: Weak<dyn ZombieTrait>, ...fields }
impl Deref for Zombie { type Target = Monster; ... }   // inherited fields and methods: self.level, self.get_x()
pub trait ZombieTrait: MonsterTrait { fn as_zombie(&self) -> &Zombie; /* virtual methods Zombie adds */ }
impl Deref for dyn ZombieTrait { type Target = Zombie; ... }  // non-virtual methods on a JRef<dyn ZombieTrait>
impl Zombie { pub fn tick(&self) { ... } ... }         // the bodies, as inherent methods
impl EntityTrait for Zombie { fn tick(&self) { Zombie::tick(self) } ... }   // generated glue
```

- A class's method bodies are inherent methods on its struct. The traits (`EntityTrait`...) carry the
  virtual methods; the generated glue at the bottom of each concrete class's file forwards each one to the
  nearest class that declares it. **Inside a body, call virtual methods on `this` through `self.this()`**
  (`this.tick()` -> `self.this().tick()`), so an override in a subclass runs; `super.tick()` ->
  `self.base.tick()` (the parent's inherent body). Private, final and static methods: call them directly.
- Polymorphic constructors: `Zombie::new_base(this: &Weak<S>, args...) -> Zombie` builds the struct
  (`base: Monster::new_base(this, ...)`); concrete classes also get `Zombie::new(args) -> JRef<Zombie>`
  (`Arc::new_cyclic`). Non-polymorphic classes: `C::new(args) -> JRef<C>` with `Arc::new_cyclic(|this| C { this: this.clone(), .. })`.
  Overloaded constructors: `new`, `new_3`... (by arity). Virtual calls a Java constructor makes
  (`this.defineSynchedData(...)`) cannot run before the `Arc` exists: do them right after `new_cyclic`
  in `new`.
- `instanceof` / casts: `cast::<dyn MobTrait, _>(&entity)` -> `Option<JRef<dyn MobTrait>>`,
  `cast::<Zombie, _>(&e)` for a concrete class, `instance_of::<..>`. Every type lists what it can be cast to
  with `jobject!(Type: dyn Trait, dyn Interface...)` (generated). Upcasts are coercions:
  `let e: JRef<dyn EntityTrait> = zombie;`.
- `==` on references: `same(&a, &b)` (or `Arc::ptr_eq`). Identity-keyed maps: `ById<T>` keys.
- Interfaces are traits; default methods are trait default bodies; static interface methods are free
  functions in the interface's module. A single-abstract-method interface is implemented for closures.
- Anonymous classes (`new Goal() { ... }`) become a private struct in the same module implementing the
  traits (copy the glue of a sibling concrete class).
- Generic methods (`<T> T get(...)`) are not in the traits (Rust's trait objects can't have them): they are
  inherent on the declaring class.

## Statics

- `static final` constants with literal values are `pub const`; other statics are module-level
  `pub static NAME: LazyLock<T> = LazyLock::new(|| ...)` (mutable ones `LazyLock<Mut<T>>` or atomics).
  Static fields of a nested type are prefixed with its name (`MUTABLE_BLOCK_POS_FOO`).
- Static methods are associated functions (`Blocks::register(...)`, `Mth::floor(x)`); static fields are
  reached through the module (`blocks::STONE`, `mth::PI`).
- Registration order matters (`Blocks`, `Items`, registries): the bootstrap forces the `LazyLock`s in
  Java's static-initialization order, as `Bootstrap.bootStrap()` does.

## Behaviour

- Port every line, in order: same RNG draws (`RandomSource`), same `Math`/`Mth` calls, float vs double as
  Java has them (`f32` math stays `f32`). Java's int arithmetic wraps: this crate is built with
  `overflow-checks = false`, so `+ - *` wrap as in Java; `>>>` is `((x as u32) >> n) as i32`; `/` and `%`
  by zero panic as Java throws. Casts `(int) d` are `d as i32` (saturating, as Java).
- Exceptions: methods declared `throws` return `Result<T, Throwable>`; `throw` of an unchecked exception is
  `panic!`, and a `catch` of one is `std::panic::catch_unwind` only where the Java code relies on it (the
  tick loop's crash reports, command parsing). Checked ones propagate with `?`.
- Logging: `LOGGER.info("x {}", a)` -> `log::info!("x {}", a)` (the `LOGGER` fields are dropped).
- Streams -> iterator chains; lambdas -> closures (`Arc::new(move |x| ...)` where a `JRef<dyn Fn-trait>` is
  expected); `switch` -> `match`.
- Bukkit/Paper API calls inside NMS stay: `this.getBukkitEntity()` ->
  `api::<dyn crate::org::bukkit::entity::Entity, _>(&self.this())` (the NMS entity *is* the API object; use
  the API trait the Java code's static type names, e.g. `dyn crate::org::bukkit::entity::Player` for a
  `CraftPlayer`), `CraftEventFactory.callX(...)` -> `crate::api_impl::event::CraftEventFactory::call_x(...)`,
  `new PlayerMoveEvent(...)` -> the API event struct, `.callEvent()` as in Java. `CraftX.getHandle()` and
  `CraftX` casts disappear: the value already is the NMS object.
- Leaf/Paper/Purpur/Gale config reads (`org.dreeam.leaf.config...`, `GlobalConfiguration.get()`,
  `level.paperConfig()`, `PurpurConfig`) stay; they are ported with their YAML files.
- Mojang's game data (`data/`, `assets/`) is never committed: the server reads it at run time from the
  Minecraft server jar (`.local/`).

## Working in parallel

- Edit only the files of your assignment. Need something in another file (a helper, a field)? Note it
  in your report instead of editing that file, unless your assignment says otherwise.
- Keep the generated signatures; if one is wrong (a nullable that isn't marked, a parameter that Java
  mutates and so needs `&mut`), fix it in the file and say so in your report.
- No `cargo` runs while porting (one crate, many agents): check syntax per file with
  `rustfmt --edition 2024 --check <file>` (it parses only that file). The crate is compiled and fixed in
  integration rounds.
- Leave no `todo!()` you can port. If something truly can't be ported yet (a library type that doesn't
  exist yet), write the call as it will look and mark it `// PORT: <what's missing>`.

## Libraries

External libraries (DFU, Brigadier, netty, Adventure, Gson, JOML, Guava/fastutil leftovers, concurrentutil,
Configurate, authlib...) are ported **with the same rules as Leaf's own code**, as if their Java sources were
in the tree: `com/mojang/serialization/Codec.java` -> `crate::com::mojang::serialization::codec` with
`pub trait Codec<A>`, its static fields as statics of that module (`codec::INT`), methods snake_cased with
the arity rule for overloads (`optionalFieldOf(String)` -> `optional_field_of`, `optionalFieldOf(String, A)`
-> `optional_field_of_2`). Each type keeps the form the skeleton gives it (`ext_stubs.rs`): a trait
(`JRef<dyn Codec<A>>`) when in-tree classes implement it, otherwise a cheap-to-clone handle passed by value
(`DataResult<A>`, `MapCodec<A>`, `ByteBuf`, `Component`) whose clones share state where Java's references do.
A trait's generic methods (`<S> Codec<S> xmap(...)`) are inherent methods on the trait object
(`impl<A: JGeneric> dyn Codec<A> { pub fn xmap<S: JGeneric>(self: &Arc<Self>, ...) }`).

Idioms the NMS code uses everywhere (the library ports provide exactly these):

```rust
// DFU
codec::INT.clone(); codec::STRING.clone();                           // Codec.INT, Codec.STRING
X_CODEC.field_of("a").for_getter(|x: &X| x.a.clone())                 // fieldOf("a").forGetter(X::a)
RecordCodecBuilder::create(|i| i.group((f1, f2)).apply(i, |a, b| X::new(a, b)))   // group(f1, f2).apply(i, X::new)
RecordCodecBuilder::map_codec(|i| ...)                                // RecordCodecBuilder.mapCodec
c.xmap(|a| .., |b| ..); c.list_of(); c.optional_field_of("k"); c.optional_field_of_2("k", default)
c.parse(nbt_ops::INSTANCE.clone(), tag) -> DataResult<A>; c.encode_start(json_ops::INSTANCE.clone(), v) -> DataResult<JsonElement>
r.result() -> Option<A>; r.get_or_throw(); r.result_or_partial(|e| log::error!("{e}")); r.error() 
DataResult::success(x); DataResult::error(|| format!(".."));
Either::Left(a) / Either::Right(b) (enum); Pair::of(a, b) / p.get_first() / p.get_second()
// Brigadier: builders by value; command bodies return Result<i32, CommandSyntaxException>
Commands::literal("x").requires(|s| ..).then(Commands::argument("n", IntegerArgumentType::integer()).executes(|ctx| ...))
IntegerArgumentType::get_integer(ctx, "n")?
// netty: ByteBuf is a shared handle; FriendlyByteBuf wraps it as its `source` field
buf.write_byte(1); buf.read_int(); buf.readable_bytes();
// Adventure: Component is a value handle; Component::text("x"), NamedTextColor::RED
```

If the library port you need doesn't exist yet, write the call in this shape anyway; integration fixes
the rest. Library port agents: implement every Java API member the Leaf sources use (grep them), with these
idioms exactly.

## The Bukkit/Paper API

- paper-api is ported as API: interfaces are traits (already in the skeleton), classes (events, `Location`,
  `ItemStack`, `Vector`, `NamespacedKey`, configuration, `Bukkit`...) are structs with their bodies, enums
  keep their constants. `Bukkit.getServer()` returns the `JRef<dyn Server>` that `MinecraftServer` implements.
- CraftBukkit is not ported as wrapper types. Each wrapper's code becomes the impl of its API trait on the
  NMS type behind `getHandle()`, in the wrapper's own Rust file under `api_impl` (the skeleton marks wrapper
  types with a comment): `impl crate::org::bukkit::entity::Player for ServerPlayer { .. }` with
  `getHandle()` -> `self`. A wrapper hierarchy over an NMS hierarchy becomes a blanket impl keyed by the
  NMS trait: `CraftLivingEntity` -> `impl<T: LivingEntityTrait> crate::org::bukkit::entity::LivingEntity for T`
  (concrete wrappers like `CraftZombie` -> a plain impl for `Zombie`). Wrapper state (fields of a CraftX)
  goes into a struct in that file, `CraftPlayerData`, which the NMS type will hold: list those in your report.
  Wrappers of things NMS has no single object for (`CraftBlock` = level + pos, `CraftItemStack` around an
  NMS `ItemStack`, block-state snapshots, `CraftInventory` around a `Container`, item metas) stay small
  structs in `api_impl` holding the NMS values.
- The casts from NMS objects to API traits (`api::<dyn ..>(..)`) are added to the `jobject!` lines by the
  integration step, from the impls you write.

## Left out (user's decisions)

- **No data fixing.** The server runs 26.3 worlds only: DFU's datafixers (`com.mojang.datafixers` except
  `util`: `Pair`, `Either`, `Unit`), `net.minecraft.util.datafix` fixes/schemas, `DataFixers` and Paper's
  DataConverter (`ca.spottedleaf.dataconverter`) are not ported. Where Java runs data through a fixer
  (`DataFixTypes.update/updateToCurrentVersion`, `MCDataConverter.convert...`, `ChunkSystemConverters`,
  `DataFixer` fields and parameters), drop the fixer and pass the data through unchanged.
  `DataFixTypes` stays as an enum whose updates return their input.
- **No diagnostics services:** Sentry, spark, oshi (and their Leaf/Pufferfish glue) are gone; drop the calls.
- **Networking is tokio, not netty.** `ByteBuf` stays (a shared byte buffer with Netty's read/write API, used
  by `FriendlyByteBuf` and the packet codecs). The transport (`Connection`, `ServerConnectionListener`, frame,
  compression and cipher codecs, Leaf's packet interceptors) is written on tokio by the network port:
  `Connection` keeps its public methods (`send`, `send_2`..., `setup_compression`, `set_encryption_key`,
  `set_listener...`, `tick`, `disconnect`, `is_connected`, `get_remote_address`...), so packet listeners call
  it as Java does. Elsewhere, `Channel`/`ChannelFuture`/`EventLoop` uses become calls on `Connection`.
- **No status protocol, Query, RCON, JSON-RPC management, JFR.** Velocity answers server-list pings. The
  `network.protocol.status` package and `CraftRemoteConsoleCommandSender` are not ported: drop `ServerStatus`
  fields/updates (MOTD, favicon, player sample) and handle a status handshake intention by closing the
  connection. API events about list pings stay in the API but are never fired.

## Generic methods of interfaces (decided after the first units)

A generic method of an interface (`<T> void spawnParticle(Particle, Location, int, T data)`,
`<T extends Entity> T spawn(Location, Class<T>)`, `<T> BanList<T> getBanList(Type)`) is **type-erased** so
it stays callable on `dyn Trait`: each method type parameter becomes its bound's Rust type, or
`JObjectRef` when unbounded (`data: Option<JObjectRef>`, `-> JRef<dyn Entity>`, `-> JRef<dyn BanList<JObjectRef>>`);
callers downcast with `cast` where Java's caller relied on `T`. The skeleton still shows some of these as
`fn x<T: JGeneric>(..) where Self: Sized`: write implementations and calls in the erased form; the
integration step rewrites the trait declarations to match.

## Rust libraries instead of Java's (user's decision, supersedes the library rules above where they differ)

Java's own library (the JDK) and every library that has a Rust counterpart are **not ported**: the code
uses Rust's std and crates directly. `crate::java::*`, `crate::com::google::*`, `crate::org::joml`,
`crate::it::unimi::*`, Configurate/snakeyaml/configurationmaster, log4j, jline, joptsimple keep only
**type aliases and re-exports** of the Rust types (so the skeleton's signatures resolve) plus the smallest
glue Java semantics need — never a re-implementation of the Java class. In method bodies write Rust:

| Java | Rust |
|---|---|
| `Thread`, `ExecutorService`, `CompletableFuture`, locks, latches | `std::thread`, rayon/tokio, `futures`, `parking_lot`, `crossbeam` |
| `java.io` / `java.nio.file` / `Files` | `std::io`, `std::fs`, `std::path` |
| `ByteBuffer` | `bytes` or `Vec<u8>` |
| `java.time`, `SimpleDateFormat` | `chrono`, `std::time` |
| `MessageDigest`, `Cipher`, `KeyPair`, `Deflater/Inflater`, `GZIP*` | `sha1`/`sha2`/`md-5`, `aes`+`cfb8`, `rsa`, `flate2` |
| `java.util.Random` (outside the game's own `RandomSource`) | `rand` |
| `Pattern`/`Matcher` | `regex` |
| Gson `JsonElement`/`JsonObject`/`JsonArray`/`Gson` | `serde_json::Value` / `Map` / `Vec<Value>` / serde |
| JOML `Vector3f`/`Quaternionf`/`Matrix4f` | `glam::Vec3`/`Quat`/`Mat4` (`*d` -> `DVec3`...) |
| Guava/fastutil helpers, Caffeine caches | std collections/iterators, `moka` |
| YAML configs (Configurate, configurationmaster, snakeyaml, Bukkit's YamlConfiguration internals) | `serde_yaml` |
| log4j/slf4j | `log` |
| console (jline), options (joptsimple) | `rustyline` (or stdin), `clap` |

**Only NMS (and Leaf/Paper server code, plus the Bukkit/Paper API) is ported. No shaded library is ported**,
not even DFU, Brigadier, Adventure or concurrentutil: they are replaced by Rust crates (user's decision);
the network transport is tokio. The library packages under `crate::` hold only aliases/re-exports of those
crates' types.
